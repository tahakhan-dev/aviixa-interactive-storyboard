# AVIIXA Interactive Storyboard — Slice 3 build map: SURF-SA, the Super Admin platform console (19 modules)

**Scope note before anything else.** Nineteen modules means MOD-SA-01 through MOD-SA-19. MOD-SA-20 (Fundability Surface, L46324, L117248) is deliberately outside the capability numbering — L4567 states "Nineteen module identifiers; §8.20 Fundability Surface deliberately excluded", and the source's own canonical count of nineteen SA capability sections is at L21074 and L119306–L119310. Do not build a twentieth module unit.

**Count scope.** Every number in this document that is not a source-stated closed count is a count of *extracted entries* across the 36 chunks in `registries/raw/extract/`, with heavy duplication (the same rule appears as up to twenty separate `business_rules` rows). The reader aggregate — 282 workflows, 167 controls, 169 objects, 188 screens, 485 gates — is an extraction tally, not an inventory of things to build. Source-stated closed counts, which *are* build inputs, are: six ENFORCED invariants (L2143), three named access classes (L4612), three data-access layers (L21378), fifteen device command states (L42846), ten critical-class actions as stated but eleven as enumerated (L55942), two notification channels (AC-SA-14-01, L45684), eight platform floor register rows (L4562), seventeen governed settings (AC-SA-19-05, L46318), five typed memory stores (L2139), three tier bands (L2195).

**The prototype boundary, stated once and binding on every module below.** This is a browser-only static export. There is no database, no authentication, no device channel, no scheduler, no audit store. Consequently: every state in every state machine below is a *seeded fixture the user steps through*, not a computed transition; the role selector is a view-switcher, not a login; "applied", "delivered", "acknowledged", "committed" are rendered labels on fixture data; and no screen may claim a guarantee it cannot keep. Two prototype-honesty rules follow from the source itself and should be built as chrome, not as an afterthought: AC-SA-000-06 (L42884) requires every aggregate to render an as-of timestamp and to degrade as stale-with-age or unavailable, never as zero and never blank — in the prototype the as-of timestamp is a fixture value and must be labelled as one; and AC-SCOPE-033 (L2612) forbids describing the audit log anywhere as tamper-evident, chained or signed, which in a prototype extends to not describing it as append-only-enforced either. A persistent, non-dismissible prototype banner is the honest equivalent of the tenant-visible support banner: the console is showing scripted data.

**Support-not-surveillance, binding on SURF-SA specifically.** Two modules are where this surface could go wrong. MOD-SA-12 meters Worker-Shifts — AC-GOAL-060 (L2241) fixes it as "one worker attached to work in one calendar shift meters exactly one Worker-Shift regardless of run count". That is a billing unit, and the prototype must render it as one: a count on a commercial ledger, never a rate, never a per-worker series, never a comparison between workers. MOD-SA-10 renders cross-tenant comparatives, and the source already closes the door — anonymisation precedes aggregation as an enforced invariant (L45179, AC-SA-10-03 L45230), no measure exposes operational content (AC-SA-10-02 L45230), and for every console role including the root tenant memory content is "Unavailable — counts and volume only" (L97152–L97154, Support flatly Unavailable at L97155). Build no worker-level view anywhere on this surface, and no tile that could be read as one. Profile memory holds aggregates only and an individual-level profile record cannot be created (AC-SA-04-05, L43627) — that acceptance criterion is the design brief for the memory screens.

## 1. Per-module build units

### The shared idiom, decided once (this is the single most load-bearing decision in the slice)

The source contradicts itself on how a prohibition renders. L60704 renders the invariants "locked and unpressable" and L44041 gives an ENFORCED badge with a lock icon — a present but inert control. L87376 states the opposite for the same gate: allowed roles "none — it must render as an absence of control, not a disabled control". L46121 takes the absence position for audit ("no edit or delete affordance anywhere, not even greyed"), L65361 for enablement ("the enablement control is not offered at all while a scenario fails"), L97560 for anonymisation ("absence is the control"), and AC-SA-INV-003 (L47849) says the invariants have no off control, no approval path and no configuration key *on any screen*.

**Recommendation — three renderings, applied by rule, never by taste:**

- **ABSENT.** The action does not exist for anyone, including the root. Nothing is drawn; a one-line explanatory note sits where a control would be. Applies to: the six invariants (AC-SA-INV-003 L47849), atom creation (AC-SA-02-01 L43253), audit edit/delete (AC-SA-18-04 L46193, AC-SEC-701 L104169), de-anonymise/reverse anonymisation (L97560), delete or purge on any storage surface (AC-SA-17-01 L46074, control at L97037), pausing the deterministic layer (L65614), adding an outbound integration destination (L95576), per-tenant region control (L97239).
- **DISABLED WITH A NAMED REASON.** The action exists on this platform but not for this role or not in this state. The control is drawn, inert, with the reason in text. Precedent: "Create user" renders disabled for Admin with the reason "User creation is root-only" (L76133); the Observability save action disabled with "the value has no source and must be decided" (L107777); the incident close control disabled while any reconciliation item is outstanding (L90758).
- **CLASS BADGE REPLACING THE ACTION BAR.** For critical-class actions viewed by a non-root role, the action bar is replaced wholesale by "Critical class — root approval required", explicitly so that no control can be mistaken for approval (L23707).

Where the two idioms collide on the *same* object — the ENFORCED badge is both a badge and an absence — build the badge as a **status chip, not a control**: it is not focusable, has no pressed state, and carries no tooltip implying an approval path. That satisfies L44041's badge and L87376's absence simultaneously. Log it as a decision.

**One more shared rendering rule.** AC-SA-000-08 (L42886) requires every command directed at a device or tenant surface to render one of the fifteen defined command states, and forbids rendering a command as applied on evidence weaker than a device acknowledgement. The fifteen, in order, at L42846 (restated identically at L1632, L7392, L12284, L23310, L52270, L107461 and a dozen more): created, authorized, queued, available for delivery, delivered, downloaded, validated, applied, acknowledged, rejected, failed, expired, cancelled, superseded, reconciled. Build one shared `CommandState` component; MOD-SA-09, MOD-SA-13 and MOD-SA-07 all consume it.

The one-transaction guarantee is a MOD-SA-07 rendering (it is the sixth invariant), so this module's central promise is displayed from another module's screen — a cross-reference the design must make explicit.

**MOD-SA-19 — The Tenant-Configuration Registry.** SCR-SA-26 registry table, per tenant (L42818, L46246); SB-SA-19 (L46246). Three values per setting — platform default, bound, tenant current value (L46250, L116399) — across **seventeen governed settings, each with a floor-register bound (AC-SA-19-05, L46318)**. Controls: the conformance panel listing current values that fall outside a recently tightened bound (all four roles, L46246). Write classes are stated precisely and differ per column: current-value changes platform-side are Admin actions, default changes are engineering class, bound changes are critical class (AC-SA-19-07, L46318) — three different approval routes on one table, which is the interesting design problem in this module. **A looser-than-floor value is rejected at the point of entry with the bound stated and is not stored — never accepted and logged (AC-SA-19-03, L46318)**; tightening a bound surfaces non-conforming values rather than rewriting them (AC-SA-19-09). Every write path, tenant-side and platform-side, lands here and no bypass exists (AC-SA-19-02) — which makes this module the enforcement point that MOD-SA-07's floor register merely *displays*.

## 2. The shared spine

Six spine assets, built once, consumed by every module screen.

**(a) The six ENFORCED invariants** — evaluation gate, sandbox-before-publish, encryption at rest, encryption in transit, cross-tenant analytics anonymisation, one-transaction audit guarantee (L2143, restated in stable order at L12098, L14944, L21017, L54626, L66460, L84761, L108617). Rendered in MOD-SA-07 (primary, L42800), MOD-SA-05 (evaluation gate and sandbox, L43799, L90550), MOD-SA-17 and MOD-SA-04 (encryption and anonymisation locked rows, L103982), MOD-SA-01 (security-posture panel, L105076), MOD-SA-18 (the sixth invariant is its own guarantee, L46193), MOD-SA-08 (the approval control that cannot exist, L48793). The invariant check is **step 1 of the fourteen-step effective-control evaluation order** (L46550) — in the prototype this means: resolve invariant first, then everything else, in every place a capability's availability is computed from fixture data.

**(b) The three named access classes and the three-layer data model.** Support session, compliance-emergency path, JBS access grant (L4612) — nothing else reaches record-level content, on any screen or API (AC-SEC-801, L104316). Layer 1 telemetry (counts, rates, statuses, never operational content), layer 2 anonymised comparatives, layer 3 sessions (L21378, L54954, L76100). Touches MOD-SA-15 and MOD-SA-16 (owners), MOD-SA-01 and MOD-SA-10 (layer 1 and 2 producers), MOD-SA-09 (the tenant detail page's read-only Operations tab is the place a designer will try to break this), MOD-SA-18 (every class mirrors, and no filter or export can omit a class — AC-4873, L107886).

**(c) The maker-checker and change-class spine.** Four classes: Band B routine (auto-applies, audited), engineering class (Admin approves), critical class (root approves), root-only administrative (no proposal path) — L21026. Owned by MOD-SA-08; consumed by MOD-SA-02, 03, 04, 05, 07, 09, 11, 13, 14, 16, 17, 19. Every mutating control on this surface says "Submit for approval", never "Save" or "Apply" (L15922), and shows "Submitted for Admin approval" with a request identifier in place of "Applied" (L14574). The critical-class list is the routing table: eleven items enumerated where the source says ten (L55942).

**(d) The tenant lifecycle and tier model.** OBJ-SA-TENANT's eight states (L45003) feed the tenant filter in MOD-SA-01, 09, 10, 12, 13, 15, 17. Tier bands and the usage ladder (L2195, L45354) feed MOD-SA-11, 12 and the tenant detail Overview tab. Suspension semantics are per-state and per-role and are fully enumerated at L64941–L64951 for Supervisor, Worker, Quality Manager and Tenant Admin — with the Read-only Auditor's cells simply absent from the source.

**(e) The fifteen-state command vocabulary and the honesty rule** (L42846, AC-SA-000-08 at L42886). MOD-SA-13 owns it; MOD-SA-09 (suspension and lock), MOD-SA-07 (severity catalog and locale pack distribution), MOD-SA-17 (wipe on archival) all render it. One component, one fixture shape.

**(f) The ten FB-SA fallback contracts** (L42858–L42867), which are the console's entire error-state design and should be built as a shared degraded-state kit: FB-SA-01 aggregate degraded → "measure unavailable", never a zero, never a blank; FB-SA-02 approval write failure → object unchanged, request visibly pending; FB-SA-03 audit write failure → the action does not happen; FB-SA-04 command dispatch → non-applied state displayed as such; FB-SA-05 session failure → session closed, no write capability ever existed, banner cleared only on confirmation; FB-SA-06 harness unavailable → enablement blocked, gate fails closed; FB-SA-07 delivery failure → in-app remains, failure recorded not hidden; FB-SA-08 scheduler misfire → recorded with its window; FB-SA-09 console unavailable → administration pauses, runtime and safety continue; FB-SA-10 bound validation unavailable → write refused, existing value unchanged. Every one of the nineteen modules consumes at least one.

## 3. Dependency order

The order is not the module numbering. MOD-SA-01 is numbered first and must be built last.

**Phase 0 — console shell.** Role switcher (four roles, L60698), navigation across both bands, the prohibition-rendering kit from §1, the fifteen-state command chip, the FB-SA degraded-state kit, the fixture store. Edge: every module below draws from this; nothing is decidable per-module.

**1. MOD-SA-08** — because every mutating control in every other module routes into its approval queue (L44718, L15360) and no other module can render "Submitted for Admin approval" (L14574) or the critical-class badge (L23707) before the queue and the four-role matrix exist.

**2. MOD-SA-07** — because the invariant check is step 1 of control resolution (L46550) and the ENFORCED chip is referenced from six other modules' screens. Depends on 08 for the change-class routing of the ten settings categories.

**3. MOD-SA-19** — because it, not 07, is the single enforcement point every write lands at (AC-SA-19-02, L46318). 07 displays the floor register; 19 rejects against it. Building 19 after 07 means the reject-at-entry idiom is written once and reused by 09, 11, 13, 17.

**4. MOD-SA-18** — because every control's confirmation copy names an audit event, and the audit fixtures are only meaningful once 08, 07 and 19 have produced actions to record. Its own screen is thin (filters plus export); its value is as a destination link from everywhere else.

**5. MOD-SA-09** — because the tenant object is the filter dimension for 10, 12, 13, 14, 15, 16, 17 and the row every one of them starts from.

**6. MOD-SA-11**, then **7. MOD-SA-12** — 11 supplies the entitlement and cap values 09 assigns at tenant creation; 12's ladder thresholds are the cap values 11 publishes (L45354). 11 depends on 08 for critical-class publication.

**8. MOD-SA-05** — before any capability module, because the gate view is the state those modules render and the enablement control is *absent* while a scenario fails (L65361). Build the verdict fixture before the things it gates.

**9. MOD-SA-02** — needs 05's verdicts and 08's queue. **10. MOD-SA-03** — needs 02, because an agent's capability scope is a set of atoms (L43358), and 05. **11. MOD-SA-04** — needs 03, because memory grants are fields on the agent record. **12. MOD-SA-06** — needs 03, because a trace is produced by an agent run.

**13. MOD-SA-13** — needs 09 (tenant), 07 (device policy layer), and the command vocabulary. **14. MOD-SA-15**, then **15. MOD-SA-16** — 15 needs 09 and 18 (mirroring is a precondition of the read, L14886); 16 reuses 15's session machinery and adds only the grant lifecycle.

**16. MOD-SA-17** — needs 09 (archival is a tenant state), 19 (the retention bound), 08 (critical class for legal hold, erasure, retention changes). **17. MOD-SA-14** — needs 09 for the audience snapshot and 08 for all-tenant critical class.

**18. MOD-SA-10** — read-only and derived; its only two onward actions land in 18 and 15 (L107350), so both must exist first.

**19. MOD-SA-01** — last. Its purpose is to aggregate the other eighteen (L42979: is the platform healthy, are the agents behaving, is anything waiting), it has exactly one control of its own (L47767), and every tile on it is a summary of a state machine that lives somewhere else. Building it first produces a dashboard of invented numbers; building it last makes it a genuine index of the prototype.

## 4. Conflicts and silences, with recommendations

Each becomes a numbered decision in the spec. None may be resolved silently in code.

**C1 — Two incompatible SCR-SA numbering schemes.** The chapter-22 inventory numbers 26 screens (L42793–L42818): SCR-SA-01 Overview, 08 Platform settings, 10 Floor register, 11 Emergency pause, 25 Platform audit. The chapter-24 inventory numbers 22 (L48730–L48751): SCR-SA-01 Console sign-in, 02 Overview, 09 Console users, 10 Approval queue, 21 Platform audit. Only SCR-SA-08 means the same thing in both. **Recommend the 26-screen chapter-22 scheme as canonical** — it is the fuller inventory, it is anchored on module_id in more entries, and it is the one the failure contracts and storyboards cite. Record the 22-screen scheme as a cross-reference table so any ticket citing the other numbering resolves. Never cite a bare SCR-SA-NN in the spec without the screen name beside it.

**C2 — Disabled control versus absence of control** (L60704/L44041 versus L87376/L46121/L65361/L97560). **Recommended:** the three-rendering rule in §1. This is decision one because it changes every screen.

**C3 — Three incompatible audit-entry state vocabularies.** committed only (L46141); written (L21299); committed/refused/parked (L74127) — and "parked" directly contradicts FB-SA-03 (L46191), which states there is no queued-audit path. **Recommend "committed" alone** (L46141), because the source explains *why* it is alone — no other state exists by construction — and because parked cannot coexist with the one-transaction guarantee.

**C4 — Platform audit event class count: 20 (L46178, with AC-SA-18-03 and TEST-SA-18-N1 both asserting twenty) versus 22 (L47835, L48838, AC-SCR-SA-001 at L48848), and the class list itself is nowhere in the extract.** This blocks the MOD-SA-18 filter and the class-filtered export. **Recommend: build the filter as a data-driven list from a fixture file, seed it with the classes that are actually named in the source (locked-setting-attempt at L104033, the three access classes at L107886, approvals, tenant lifecycle, device commands), label the fixture "provisional — class list and count unresolved, see L46178 vs L47835", and put the count nowhere in the UI.** A prototype that shows "22 classes" makes a claim the source cannot support.

**C5 — Three incompatible incident vocabularies plus a proposed severity scheme.** OBJ-SA-INCIDENT open/acknowledged/investigating/mitigated/resolved/closed (L42991); the unbound record classified/owned/degraded mode/verified/reconciled/closed (L107949); OBJ-AI-INCIDENT Detected/Open/Escalated/PlatformIncident/Resolved (L88737); four platform incident levels marked *proposed* (L107904). **Recommend OBJ-SA-INCIDENT** — it is the only one anchored to a MOD-SA-01 object card — and treat the L107949 fields (classification, owner, detection source, communication decision, verification checklist) as *required attributes* of that object rather than as states, which is what AC-4880 (L107967) actually needs. Do not render incident levels at all; they are proposed.

**C6 — WF-PLT-009 is claimed by two modules** (MOD-SA-01's key_functions at L55259, and a MOD-SA-03 anchor on its own line at L55295). **Recommend MOD-SA-01** — the AI outage's console home is the health view; MOD-SA-03 renders agent state, not incident ownership. Cross-link.

**C7 — WF-FEAT-002 and WF-FEAT-005 have no owner.** MOD-SA-07's key_functions name 001/003/004 and skip 002 (L54620); the modules anchored on WF-FEAT-002's line are MOD-SA-11 and MOD-SA-19 (L54658); 005 (L54770) is named by nobody. **Recommend: per-tenant feature override belongs to MOD-SA-11** — the override is a flag on the tenant record, not a platform setting (AC-SA-11-04, L45342), and the tenant feature panel is already a MOD-SA-11 screen (L54606). Global feature control stays in MOD-SA-07.

**C8 — DEC-PAUSE-001, who may initiate the emergency pause, is open (L87799)**, and the controls disagree: root only (L54979, L65613), Admin proposes/root approves (L104586), root or Admin (L110543), Platform Engineer proposes only (L91287). **Recommend Admin proposes, root approves** — it is the only option consistent with the canon's rule that no fallback may depend indefinitely on one person, and with WF-PLT-006's stated actors (L55188). Render Platform Engineer's control as DISABLED with "proposal only — pending DEC-PAUSE-001". Separately, DEC-KILL-001 (L87795) leaves the runaway-loop kill switch's relationship to the pause unstated and the source *warns they must not be conflated* — build them as two visibly different controls in two different categories, or build only the pause and label the kill switch as undecided.

**C9 — Does a Trace Viewer screen exist at V1?** Six sources say no (L42799, L43885, L47798, L48736, L86043, L4682); four describe a screen or a control (L57772, L65489, L97154, L2173). **Recommend no viewer screen**, per §1: build SB-SA-06 as the honest absence plus the decision record. Note that DEC-SEC-020 (L104506) independently warns that an unqualified trace viewer "becomes the ambient-browsing path the source forbids" — which is a second, stronger reason not to build it.

**C10 — DEC-AUDIT-001: immutability claimed, tamper-evidence deferred** (L104066, L118587, L2612). AC-SA-18-10 is the one rule in MOD-SA-18's set flagged as *not* a hard gate — it is a scope disclaimer. **Recommend: the UI never uses the words tamper-evident, chained, signed, or verified.** "Append-only" is permitted as a stated design property; in the prototype, add "(prototype — no store behind this)".

**C11 — DEC-ERASEAUD-001 and DEC-ANON-001** pit audit immutability against erasure and 24-month anonymisation (L97689, L74786). L8368 asserts the resolution as fact ("never rewrites audit rows") while the decision record still reads open. **Recommend the L8368 reading — anonymisation operates on the identity-resolution layer, never on audit rows** — and say so on screen, because it is the only reading that keeps both AC-SA-17-06 and AC-SA-18-04 true.

**C12 — The critical-class list says ten and enumerates eleven** (L55942, restated as ten at L21015 and L44720). **Recommend building the eleven** and flagging the count discrepancy; the approval routing table is unbuildable from a list that is short by one, and dropping an item silently would drop a root approval.

**C13 — DEC-ROOTSUCC-001 / DEC-ROOTSOD-001** (L55989, L21146): the root approves its own critical actions because no second critical approver is assigned, against an otherwise-absolute self-approval prohibition; root unavailability freezes emergency pause, severity catalog, floor register, compliance suspension, device wipe, retention and legal hold. **Recommend: build the root-unavailable state as a first-class, visible screen state** on the approval queue ("critical class frozen — no second approver exists, DEC-ROOTSUCC-001"), rather than pretending the queue always drains. It is the most honest thing this prototype can show about the design.

**C14 — DEC-FEAT-001** (L21098, L46211): §8.8.3 makes the Admin the approver of a Platform Engineer's enablement change; §8.19 makes platform-side enablement an Admin action outright. **Recommend the recorded recommendation at L46668 — split by kind: capability-level controls follow the Engineer-to-Admin path, commercial entitlement controls are Admin actions.** It resolves both readings without inventing a third.

**C15 — MOD-SA-04 has zero controls** (verified against both the 759-entry raw and 608-entry deduplicated control inventories). **Recommend the read-only policy-card build in §1**, with an explicit "unspecified in source" panel listing the four missing affordances (set per-type retention default, edit redaction policy, trigger re-index, footprint dimensions). A prototype that invents four memory controls is a prototype that ships a fiction.

**C16 — MOD-SA-01 has one control.** Same treatment: build the minimum forced by the acceptance criteria, and label the rest as unspecified. Do not invent acknowledge, assign, escalate.

**C17 — Roles_allowed is inconsistent for every module.** MOD-SA-01 is stated four ways; MOD-SA-07 ranges from root-only (L11664) to all four (L21084); MOD-SA-18 from two (L2442) to six including tenant-side mirrored readers (L46125); several are empty at L98229–L98247 and L116399. **Recommend: the module-level roles_allowed array is not authoritative anywhere. Drive every affordance from the per-control allowed-roles values, which are specific and mostly consistent, and grant all four console roles *read* access to every screen unless a control or a rule says otherwise** — which is exactly what the four-role chapter-22 cut (L42742–L42753) does.

**C18 — Platform Engineer and support sessions, direct conflict.** L20740 forbids Platform Engineer from entering tenant context under any access class; L65401 and L117322 allow a read-only support session. **Recommend the prohibition (L20740)**: Band A/Band B separation is the stronger and more frequently restated principle, and the narrower grant is the safer prototype. Render the control as ABSENT for Platform Engineer with a note naming the conflict.

**C19 — Support session extension and export are both open** (DEC-SUPEXT-001 L16122, DEC-SUPEXP-001 L16123). **Recommend: no extension (a new session with a fresh reason, per AC-WF-ROLE-024-01 at L56107) and no export from inside a session** — the recommendation already on record, and the only one that keeps the mirroring guarantee (L14886) intact.

**C20 — Compliance-emergency time box is not stated.** The two-hour default belongs to normal support sessions only; DEC-SEC-017 is open (L104216). **Recommend rendering the field as required-and-unset ("Not yet set — DEC-SEC-017"), following the idiom at L90030**, rather than hard-coding the one-hour recommendation from L19733.

**C21 — Tenant detail page: "eight tabs" but seven enumerated.** L42807 and L44984 say eight; the enumeration at L7629 and L52383 gives seven — Overview, Operations (read-only), Agents, Memory, Devices, Metrics, Logs and Audit. **Recommend building the seven that are named and flagging the eighth as unresolved.** The likeliest missing tab, by adjacency, is Tier/Commercial or Configuration, but the source does not say so and the prototype must not guess.

**C22 — MOD-SA-07 is "ten categories" but has fifteen acceptance-criteria sub-groups** (L44633 versus AC-SA-07-01-xx through -15-xx at L44051–L44627). **Recommend: ten navigable categories, with 23.7.11–23.7.15 (severity catalog, locale packs, invariants and floor register, emergency pause, settings-as-approvable-objects) rendered as the module's cross-cutting sections rather than as an eleventh through fifteenth category** — which matches the screen inventory, where the catalog, register and pause each have their own SCR-SA number (L42801–L42803).

**C23 — The MOD-SA-07 scheduled-work and feature-control material is classified "User-Mandated Product Extension", not SoW Fact** (L54620, L98419). **Recommend building it visibly separated and labelled**, so the client can see what is contract and what is extension.

**C24 — Eight acceptance criteria for MOD-SA-01 are indexed but never extracted** (AC-SA-01-01..08 at L43068–L43075), as are AC-SA-000-02/-04/-09, AC-SA-18-03/-07/-09, five each of AC-SA-05 and AC-SA-06, sixteen of the AC-SA-02/03/04 set, and AC-SEC-805. **Recommendation: before the spec is written, someone reads those exact source lines.** MOD-SA-01's entire module-level acceptance set is missing from the structured data, and it is the module with one control — the two facts are probably related.

**C25 — The eight per-surface access classes are named once (L16178, L17213) and never defined.** No passage maps them onto the three named platform access classes. **Recommend: do not use the eight anywhere in this slice.** Any mapping would be an inference the source does not make. The permission-matrix cell status set is a third, separate vocabulary whose own membership varies from five to nine tokens across passages (L1200, L10238, L61167) — pick the nine-token cut (L10238), which is the most frequently restated, and record it.

## 5. The honest risk list

**R1 — The prototype implies a backend it does not have, at MOD-SA-13 above all.** This module renders device commands with a fifteen-state vocabulary, wipe authority, sync-then-wipe, and an "honest not-yet-delivered indicator" (L117496). Every one of those is a claim about a real channel. The specific hazard is AC-SA-13-05 (L45570): no console view renders an unreached device as wiped. A prototype with a fixture that flips to "applied" on click violates the letter of the acceptance criterion it is meant to demonstrate. Mitigation: the fixture must *advance through* states on user action with the state name always visible, and the screen must carry the prototype banner. Same risk, lower blast radius, at MOD-SA-09 (suspension) and MOD-SA-07 (catalog and locale distribution).

**R2 — The invariants get built as disabled toggles.** This is the single most likely visual error, because a lock icon on a switch is the obvious design and it is what L44041 and L60704 literally say — while L87376 says the opposite and AC-SA-INV-003 (L47849) forbids a control, an approval path *and* a configuration key. A disabled toggle implies an enabled state exists somewhere. The status-chip resolution in §1 exists to prevent this; it needs to be in the design spec, not in a code comment.

**R3 — Someone adds an action to the tenant detail page.** AC-SA-09-14 (L45105) is a flat prohibition on operational action from that page for any console role, and eight tabs of tenant information is exactly the surface where a designer adds "suspend", "message this tenant", "open a session". The three access classes exist so that reaching tenant content is deliberate; a convenience button on the detail page destroys that. Guard it explicitly.

**R4 — Ambient browsing creeps in through a link.** Every module screen has a plausible reason to link to a tenant record: an incident to the affected run, a metric to the underlying data, an audit row to the object it names. AC-SA-000-07 (L42885) and AC-SEC-801 (L104316) forbid all of it outside a named session. The trace viewer is the named instance of this hazard (DEC-SEC-020, L104506), but the everyday instance is a metric tile with a drill-through. Rule for the build: on SURF-SA, no link ever resolves to record-level content; it resolves to a session-request form.

**R5 — Support-not-surveillance is violated by a metric, not by a feature.** Nobody will build a worker ranking screen. Someone will build a "Worker-Shifts by tenant, trending" chart, then a per-site breakdown, then a per-shift one, and the last step is per-worker. The line to hold is at the tenant: Worker-Shift is a monthly billing count (L2241) and cross-tenant comparatives are anonymised before aggregation (L45179). No time series below tenant-month, no rate, no comparison of people.

**R6 — Screen identifiers wire the wrong screen.** Two numbering schemes disagree on nearly every SCR-SA number below 26 (C1), and SCR-SA-03 alone names both the atom registry and the agent roster. Any route, ticket or test keyed to a bare number will eventually wire the atom registry to the agent roster. Mitigation: names in the spec, numbers only as annotations.

**R7 — Modules with no controls get invented affordances.** MOD-SA-04 (zero), MOD-SA-06 (zero), MOD-SA-01 (one), MOD-SA-11 (one), MOD-SA-16 (one). Under deadline these look like gaps to fill rather than findings to report. They are findings: the source is silent, and a plausible-looking invented control is worse than an empty panel, because it will be read back as a requirement.

**R8 — The approval queue is built as a formality.** Maker-checker is not a workflow decoration on this surface; it is where change class, critical-class routing, the root-unavailability freeze, self-approval refusal and the two named failure states (approved-not-applied, approved-not-executed, L55897) all live. A queue that only shows pending/approved will make eleven critical actions, three write classes in MOD-SA-19 and the entire root-succession problem invisible — which is precisely the material the storyboard exists to show.

**R9 — Counts get published.** "Twenty-two audit classes", "485 gates", "282 workflows", "ten critical actions" — every one of these is either an extraction tally or a source figure that contradicts its own enumeration. A number on a slide becomes a commitment. Publish names and line numbers; publish a count only where the source closes the set and the enumeration matches it (six invariants, three access classes, fifteen command states, two channels, five memory stores, seventeen governed settings).
